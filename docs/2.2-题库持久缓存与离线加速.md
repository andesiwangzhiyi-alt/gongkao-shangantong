# 上岸通 2.2 · 题库持久缓存与离线加速

> 日期：2026-08-19
> 目标：避免用户每次访问都重新执行约 164MB 题库 JavaScript，在不牺牲版本一致性和数据安全的前提下加快二次访问。

## 1. 原问题

v2.1 已将 35 万级大文件拆分并去重为 59,068 题，但浏览器仍需要：

1. 请求两个 manifest；
2. 加载并执行 52 个 JavaScript 分片；
3. 重新构造 45,113 道懒加载题目的对象；
4. 再展开为前端检索使用的完整题库。

HTTP 缓存只能减少重复下载，不能避免大体积 JavaScript 的解析与执行。线上首次完整加载实测约 25 秒，刷新后仍有明显等待。

## 2. 实现方案

### 2.1 IndexedDB 分块缓存

- 数据库：`shangantong-bank`
- 对象仓库：`parts`
- 缓存范围：仅 q6/q9 懒加载题库，共 45,113 题；基础真题与原创题仍由首屏脚本加载。
- 每条缓存记录最多 250 题，当前共 184 个数据块，避免单次结构化克隆过大。
- 首次网络加载完成后，缓存写入在后台进行，不延迟 `sat:bank-loaded`。
- meta 最后写入；如果写入中断，不会把半成品识别为可用缓存。

### 2.2 内容指纹与自动失效

重建脚本为 q6/q9 分片内容分别生成 SHA-256 指纹并写入 manifest：

```json
{
  "version": 4,
  "build": "内容指纹",
  "total": 43103,
  "chunks": []
}
```

前端每次只重新验证两个小型 manifest，组合出缓存签名。题库内容、题量或分片变化后，签名自动变化，旧缓存不会被加载，并无感回退网络。

### 2.3 完整性保护

缓存恢复前校验：

- 签名一致；
- meta 总题量一致；
- 每个缓存块存在；
- 每个块实际题量等于记录题量；
- 全部恢复题量等于 manifest 总题量。

任何一步失败都会清理无效缓存并回退 52 个网络分片，不会向 `QUESTION_BANK` 追加半套数据，也不会造成重复题。

### 2.4 降级与用户控制

- 不支持 IndexedDB、隐私模式限制或存储配额不足时：题库仍可通过原网络路径正常使用。
- “更多 → 题库离线加速”显示缓存状态。
- 用户可一键清理约 150MB 公共题库缓存。
- 清理题库缓存不会删除 localStorage 中的作答记录、错题本、打卡和个人画像。

### 2.5 加载进度

顶部栏增加 3px 非侵入式进度条，显示：

- `完整题库 N%`
- `✓ 完整题库已就绪`
- `⚡ 缓存题库已就绪`
- 加载失败状态

进度组件不改变移动端顶部栏宽度，完成 3.5 秒后自动隐藏。

### 2.6 自适应并发与自动重试

- 在线顺序反转基准显示：3/6/9 路并发分别约 3.30/2.60/3.53 秒，6 路最稳定。
- 普通设备并发加载 6 个分片；设备内存不高于 2GB 时降为 3 路；省流模式或 2G 网络降为 2 路。
- 单个分片瞬时失败时自动重试两次（总计最多 3 次），等待 500ms、1000ms；已加载分片不会重复执行。
- 重试过程通过顶部进度条显示，不会立即中止整库加载。

## 3. 验收结果

本地 Chrome 自动化实测：

- 首次网络加载：约 0.9–1.7 秒（本机 HTTP 服务）；线上 6 路模拟约 2.60 秒
- IndexedDB 恢复：本机约 0.36–0.65 秒；已发布版线上实测 0.513 秒
- 已发布版二次访问加速：约 35.35 倍（18.134 秒 → 0.513 秒）
- 缓存题量：45,113
- 完整题量：59,068
- 恢复后重复追加：0
- 版本过期自动回退：通过
- 一键清理：通过
- 清理后个人 localStorage 保留：通过
- v2.2 缓存/重试专项验收：17/17

同时保持：

- 原完整回归：48/48
- v2 定向验收：20/20
- v2.1 数据质量：18/18
- v2.1 前端验收：12/12

## 4. 后续优化方向

1. 将 q6/q9 分片从可执行 JavaScript 迁移为压缩 JSON 或二进制资源，进一步降低首次解析成本。
2. 按模块按需加载，而非所有功能都等待全库。
3. 为高频搜索建立轻量倒排索引并单独持久化。
4. 评估 Service Worker 离线壳层缓存，使断网时首页和已缓存题库均可使用。
