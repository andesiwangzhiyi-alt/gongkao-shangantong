## 0A. 2026-08-19 实施结果（v2.1）

本报告中的高优先级问题已完成修复并通过自动化验收：

- **题库精确去重**：185,258 道参与重建，保留 58,978 道结构化题；加 90 道原创题，前端总题量 **59,068**。按“归一化题干 + 图片指纹 + 选项集合”保守合并，验收重复数为 **0**。
- **多来源聚合**：37,204 道题包含多个来源；每个真题/模考来源均保存来源名称、年份、地区、考试类型及对应原卷题号 `num`。
- **内容清洗**：`视频解析`、`来源…第N题笔记`、材料冗余引导词、`复制高亮`均清零；选项 `[图]` 无图残留为 0。
- **图片链路**：在线选项不再显示 `[图]`；`printPaper()` 与 `printFiltered()` 输出真实 `<img>`，加入 `<base href>`，并在图片加载完成后再调用打印（最长等待 4 秒）。
- **搜索与标签**：新增标签/来源关键词检索；搜索覆盖 `tag/src/srcs/考点/题干/选项/解析`；多来源以“年份·考试·地区/卷别·第N题”标签展示。
- **移动端 UI**：390px 下首页、刷题、申论、更多页根文档均无横向溢出；修复趋势条、日历和申论导航的容器约束。
- **体积**：题库 JS 目录降至约 **164MB**，显著低于去重前约 380MB 量级。
- **验收**：原回归 48/48、v2 定向 20/20、v2.1 数据质量 18/18、v2.1 前端 12/12，合计 **98/98**。

## 1. UI 界面不理想

### 1.1 实测证据（Playwright 布局审计，390×844 / 768×1024 / 1280×800）

| 视口 | 页面 | 检测结果 |
|---|---|---|
| 390px | 首页 | **横向溢出** scrollW=474 > 390；`.rate-col`/`.bar`/`.lb`（14天趋势条）溢出；`.card` 360<459、`.rate-bar` 328<443 被裁切 |
| 390px | 每日一练 | `.cal-wrap` 328<640 —— 日历固定 640px 宽被裁切；`.cal-grid`/`.cal-cell` 溢出 |
| 390px | 更多 | 同上，`.cal-wrap` 328<640 溢出 |
| 390px | 申论 | `.sl-nav` 328<507 —— 分类导航固定 507px 被裁切；`.chip` 按钮溢出 |
| 390px | 答题层 | `.cal-wrap` 328<640（答题层内残留日历，疑似复用视图） |
| 1280px | 首页 | `.hero` 832<862 —— hero 内容被容器裁切 30px |
| 1280px | 首页 | `.hero` 832<862 |

### 1.2 根因

1. **首页 14 天趋势图**（`renderDash()` → `last14Bars()`）：每个 `.rate-col` 有 `min-width` 或 padding，14 列在 390px 下超宽，且容器 `.rate-bar` 无 `overflow-x:auto` 兜底、无窄屏 `grid-template-columns:repeat(7,1fr)` 之类压缩。文件：`js/app.js` 的 `last14Bars()` + `css/style.css` 的 `.rate-bar` 规则。
2. **日历固定 640px**：`css/style.css` 中 `.cal-wrap` 被设了固定宽度（约 640px），缺少 `<640px` 的 media query 把它改为百分比/`min-width:0`。文件：`css/style.css`。
3. **申论分类导航固定 507px**：`.sl-nav` 固定宽度 + `.chip` 内边距过大，未做换行或横向滚动。文件：`css/style.css`、`js/app.js` 的 `renderShenlun()`。
4. **桌面 hero 裁切**：`.hero` 内容（标题+副标题+提示）比容器宽 30px，可能是内部 flex 项 `flex-shrink:0` 或白空间未折行。

### 1.3 修复建议

| 项 | 建议 | 优先级 |
|---|---|---|
| 14 天趋势条 | `.rate-bar{overflow-x:auto}` + `.rate-col{flex:1 1 0;min-width:0}`；390px 下每格 ≤7px | P0 |
| 日历 | `.cal-wrap{width:100%;max-width:100%}` + 窄屏 `.cal-cell{padding:4px}`；或改 `grid-template-columns:repeat(7,minmax(0,1fr))` | P0 |
| 申论导航 | `.sl-nav{flex-wrap:wrap}` 或 `overflow-x:auto`；`.chip` 加 `white-space:nowrap;flex-shrink:0` | P0 |
| hero | `.hero` 加 `min-width:0` + 内部 `word-break:break-word`；或缩减内边距 | P1 |
| 通用 | 全站 `html,body{overflow-x:hidden}` 兜底；`*{box-sizing:border-box}` 全局校验 | P1 |

> 注：除布局缺陷外，UI"不理想"还包含**视觉设计层面**的主观问题（配色、卡片层次、间距节奏）。建议在 3.0 UI 打磨阶段整体走查，可参考 `docs/screenshots/` 现有截图逐屏对比。

## 2. 题库加载太慢

### 2.1 实测数据（本机 127.0.0.1 无缓存场景）

| 指标 | 实测值 |
|---|---|
| DOMContentLoaded | 3.99s |
| 首页可见（.hero 出现） | 5.86s |
| 完整题库加载（39 分片，本地） | 4.0s（39/39 分片） |
| 全库检索"中国" | 42ms（13,327 题命中） |

> 本机 localhost 带宽约 87MB/s，所以 348MB 只花 4s。**GitHub Pages 从国内访问会放大数倍到数十倍**——这是用户体感"加载太慢"的根本原因。

### 2.2 结构性根因

1. **首屏同步加载 ~28MB JS**（`index.html`）：
   - `questions.js`(24KB) + `questions2.js`(15KB) + `questions3.js`(8KB) + `questions4.js`(640KB) + **`questions5.js`(12MB)** + `questions7.js`(15MB) + `shenlun.js`(8KB) + `app.js`(80KB)
   - 全部是 `<script>` 阻塞式同步加载 → 浏览器必须下载+解析完 ~28MB 才能渲染首页。**questions5/questions7 完全可以在懒加载体系内。**

2. **348MB 模考库无持久化**（`js/lazy-bank.js`）：
   - 当前实现：fetch manifest → 39 个分片按每批 3 个 `<script>` 注入，**纯 HTTP 缓存**。
   - 每次新开页面（或浏览器清缓存）都要重新下载 348MB。
   - 没有 IndexedDB / Cache Storage / localStorage 做跨会话持久化。
   - 39 个分片是"每批 3 个"串行，吞吐受限；分片未 gzip/压缩。

3. **用户在题库未就绪前点刷题/模考** → `requireFullBank()` 弹 toast"正在加载完整题库，请稍候…"，并 `ensureFullBank().then(...)` 等待，**体验上是"卡住等 348MB"**。

### 2.3 修复建议（按收益排序）

| 方案 | 做法 | 预期收益 | 优先级 |
|---|---|---|---|
| **IndexedDB 持久化** | 首次加载后把 39 个分片内容以 `string` 存 IndexedDB；后续访问直接 `eval` 本地数据，0 网络 | 二次访问从 4s→<1s（本机）/ 公网从几十秒→<1s | P0 |
| **分模块懒加载** | manifest 按 module 分组；只加载当前需要的模块（如先 常识+言语），做题到哪个模块再补 | 首屏 + 前几个模块快速可用 | P0 |
| **首屏瘦身** | questions5/questions7 也改成懒加载；首页只依赖原创题库（questions.js~4.js，共 ~700KB）+ 一个"完整题库加载中"占位 | DOMContentLoaded 从 4s→<1.5s | P0 |
| **gzip 压缩分片** | 部署层开 gzip/brotli（GitHub Pages 自动对 .js 开 gzip），或本地生成 .gz 并配置 | 传输量 348MB→~60MB | P1 |
| **合并小分片** | 39 分片 → 按模块约 10-14 个；或保持但去掉每批 3 个的等待，改为 `requestIdleCallback` 里连续注入 | 减少请求数/调度抖动 | P1 |
| **进度反馈** | 加载时展示 `loadedChunks/totalChunks` 进度条，而不是只弹 toast | 体验可预期 | P1 |

> **验收标准**：二次访问（IndexedDB 命中）从打开到可刷题 < 2s；首屏 DOMContentLoaded < 1.5s；任意模块做题无需等待全库。

## 3. 导出试卷无图片 + 乱码

### 3.1 无图片根因（代码级）

`js/app.js` 的 `printPaper()`（打印/PDF 导出）第 766-768 行：

```js
(mat ? `<div class="material">${esc(mat).replace(/\[图\]/g,'（图）')}</div>` : '') +
`<div class="q">${srcNote(q)}<span class="no">${no}.</span>
 <div class="stem">${esc(q.stem).replace(/\[图(\d+)\]/g,'（图）')}</div>
 <div class="opts">${q.options.map((o,j)=>`<div>${'ABCD'[j]}. ${esc(o)}</div>`).join('')}</div></div>`
```

**所有图片占位 `[图N]`/`[图]` 被替换成字面文字"（图）"**，导出卷完全无图。同理 `printFiltered()` 也做了类似处理。

进一步看，即便不加"（图）"，`window.open+document.write` 的打印窗口里 `<img>` 引用的是：
- 国考真题：本地 `assets/img/*.png`（相对路径）→ 打印窗口无 base 路径，需加 `<base href>` 才能加载
- 模考题：在线 `https://fb.fbstatic.cn/...`（实测可直连，无防盗链）→ 打印时若图片未加载完就 `window.print()` 会空白

### 3.2 乱码根因（数据级）

导出答案页（第 781 行）直接渲染 `esc(q.analysis)`，而题库数据中：

| 残留类型 | 数量 | 示例 |
|---|---|---|
| 解析尾部"来源20XX…第X题笔记"垃圾 | **144,386 / 153,294**（模考 139,596 + 国考真题 4,790） | `…考点其他建设来源2022上半年省考第一季行测模考大赛（四川卷）第1题笔记` |
| 解析中"视频解析"前缀 | 9,224（模考 5,244 + 国考真题 3,980） | `【正确率 76%｜考点：常规翻译】\n视频解析第一步：翻译题干。…` |
| 选项文本 `[图]` 字面量 | 11,564（模考分片） | `该卫星将实现国际首次太阳[图]波段光谱成像的空间探测` |
| 材料冗余前缀 | 135（模考 10 + 国考真题 125） | `材料根据所给材料，回答下列问题：` |

"来源20XX…笔记"来自粉笔解析页 DOM 的**尾部面包屑/元信息**被爬虫一起抓进 `analysis` 字段（爬虫提取 `.content` 时把页面底部的"来源/考点/笔记"区块一并收走）。

### 3.3 修复建议

| 项 | 做法 | 优先级 |
|---|---|---|
| **打印带图** | `printPaper()` 恢复 `<img>`：①给打印文档 `<base href="${location.href}">` 使本地 `assets/img` 生效；②`[图N]`/`[图]` 替换为 `<img src="...">`；③`window.print()` 前 `document.fonts.ready`+`img.complete` 预加载 | P0 |
| **数据清洗管线** | 写一次性清洗脚本（Python）：①解析尾部按 `来源20\d\d` 截断，移除 `考点XX来源…第X题笔记` 残留；②解析开头的 `视频解析` 移除；③选项 `[图]` 占位保留但保证在线渲染替换（见下） | P0 |
| **在线选项 `[图]` 替换** | `optImgsHtml()` 改为**在选项文本内替换 `[图]`**（像 `renderStem` 一样），而不是仅追加在文后；同时保留 `[图]` 文字本身，避免 11,564 题出现字面 `[图]` | P0 |
| **材料前缀** | 清洗时去掉"材料根据所给材料，回答下列问题："冗余前缀（保留后面的真实材料） | P2 |

> **验收标准**：导出 PDF 中带图题能显示图片；答案解析不再出现"来源…笔记""视频解析""[图]"字样。

## 4. 材料/题目混入无关词汇

### 4.1 本质

与第 3.2 节同源：**爬虫 HTML 提取时把粉笔页面的非题目元素一起收进了结构化字段**。具体三类：

1. **解析尾部面包屑**（139,596 题）：`考点{考点名}来源{考试名}第{N}题笔记` 是粉笔解析页每个 app-ti 底部的固定页脚，爬虫把 `.content` 提取到 `解析...` 结尾后，没有把页脚的"考点/来源/笔记"切断。
2. **"视频解析"按钮文案**（5,244 题）：粉笔解析区顶部有个"视频解析"折叠按钮，其文字被当成解析正文。
3. **冗余前缀"材料根据所给材料，回答下列问题："**（10 题）：材料容器自带的引导语被当成材料正文。

### 4.2 附带发现（同源问题）

- 选项文本内 `[图]` 字面量（11,564 题）在**在线做题**时也会显示出来（图片追加在选项后，占位文字没被替换），属于用户能直接看到的"乱码"。
- `allQuestions()` 展开 154,178 题时对每题做 `{...q}` 浅拷贝，一次生成 15 万对象，内存/GC 压力大（首屏 + 检索均受影响）。

### 4.3 修复建议

| 项 | 做法 | 优先级 |
|---|---|---|
| **清洗脚本**（一次性+可复用） | `scripts/clean_bank.py`：遍历 154,178 题，①analysis 尾部按 `来源20\d\d` 截断；②`^\s*视频解析` 移除；③material 去冗余前缀；④（可选）分析中出现 `\n考点` 前的"考点"若已在 `qPointOf` 提取，可保留不删（考点本身有价值） | P0 |
| **转换管线补丁** | 修改 `parse_fenbi.py`/`convert_mock.py` 的 extraction 规则，从源头阻止页脚/按钮文案进库（后续爬取不再产生） | P1 |
| **在线渲染防御** | `renderStem`/`optImgsHtml`/`renderMat` 统一加兜底：占位符匹配不到图时，`[图N]`/`[图]` 替换为"（图）"而非保留字面量 | P1 |

> **验收标准**：清洗后随机抽 200 题人工核验 0 残留；全库正则扫描"来源20\d\d|视频解析|\[图\]（无对应图）"计数为 0。
